# 要件定義書（Slack 連携 GAS アプリケーション）

本書は、`src` ディレクトリ内の既存コードおよび関連ドキュメントをリバースエンジニアリングし、本ソフトウェアの要件を定義したドキュメントです。

---

## 1. 目的

- **Slack イベント連動型ボットの基盤提供**
  - Slack の Event Subscriptions を起点として、Google Apps Script (GAS) 上でイベントを受信し、自動応答処理を行うサーバーレスなボット基盤を提供する。
- **スレッドを活用したコミュニケーション・自動応答**
  - チャンネル内の投稿に対してスレッド形式で返信を行い、チャンネルタイムラインを汚さずに情報を集約・通知する（※将来的なメッセージ要約等の機能拡張に向けたベースライン）。
- **開発・運用時のトラブルシューティング容易化**
  - Slack から受信した生データや API 送信ペイロードを Google スプレッドシートへリアルタイムに記録し、デバッグおよび実行ログのトレーサビリティを確保する。

---

## 2. 機能要件

### (1) Slack Event API URL 検証（Url Verification）機能
- Slack App 設定時に送信される URL 検証用 POST リクエスト（`type: "url_verification"`）を判定すること。
- リクエストに含まれる `challenge` 文字列を抽出し、HTTP レスポンス（プレーンテキスト形式）として即座に返却して認証を完了させること。

### (2) Slack イベント受信・フィルタリング機能
- Slack から送信されるメッセージイベントデータ（JSON）を受信・パースすること。
- **Bot 投稿除外**: `bot_id` が付与されているイベントを検知し、処理をスキップして無限ループを防止すること。
- **サブタイプ除外**: メッセージ編集・削除やチャンネル参加等のイベント（`subtype` が存在するもの）を検知し、処理をスキップすること。

### (3) メッセージ応答・スレッド返信機能
- 対象イベントから送信先チャンネル ID（`channel`）および本文（`text`）を取得すること。
- **スレッド判定**:
  - メッセージが既にスレッド内の場合は、そのスレッドタイムスタンプ（`thread_ts`）を返信先として特定すること。
  - メッセージが親投稿（単発投稿）の場合は、該当メッセージのタイムスタンプ（`ts`）をスレッド親として特定し、新規スレッドを開始すること。
- Slack Web API（`https://slack.com/api/chat.postMessage`）を呼び出し、指定のスレッド宛にメッセージを送信すること。

### (4) スプレッドシート・ロギング機能
- 外部から受信したリクエスト本文（`e.postData`）を Google スプレッドシートの末尾行に追記すること。
- Slack API 呼び出し時のリクエストヘッダーおよび送信ペイロード（`ApiParams`）をスプレッドシートの末尾行に追記すること。
- 処理実行中に例外が発生した場合、エラー内容をスプレッドシートおよび GAS コンソール（Stackdriver Logging）に記録すること。

### (5) 環境設定・シークレット管理機能
- 外部 API トークンや連携先スプレッドシートの識別情報を、GAS のスクリプトプロパティ（`PropertiesService`）から安全に取得・管理すること。

---

## 3. 非機能要件

### (1) 実行環境・互換性
- **プラットフォーム**: Google Apps Script (GAS) 上で動作すること。
- **ランタイム**: JavaScript V8 ランタイムに対応していること。
- **タイムゾーン**: `Asia/Tokyo`（日本標準時: JST）環境で実行されること。

### (2) 保守性・拡張性
- **TypeScript 活用**: 型定義（`SlackMessage`, `Headers`, `ApiParams`）により、データ構造の堅牢性と開発時の保守性を担保すること。
- **モジュール分割**:
  - エントリポイントおよびロギング（`Index.ts`）
  - 環境設定管理（`Config.ts`）
  - Slack API 通信ロジック（`SlackMessage.ts`）
  に責務を分離し、将来的な要約ロジックや外部 AI API 連携等の機能追加が容易な構成とすること。

### (3) 可用性・エラーハンドリング
- メイン処理（メッセージ応答処理）を `try-catch` 構文でカプセル化し、予期せぬ例外が発生した場合でもシステムが異常終了せず、エラーログを記録して安全に復帰すること。

### (4) セキュリティ
- **認証情報の保護**: Slack Bot トークン等の機密情報をソースコード上にハードコードせず、スクリプトプロパティ経由で秘匿化すること。
- **API 通信**: Slack Web API との通信は HTTPS プロトコルおよび Bearer トークン認可を用いて安全に行うこと。

---

## 4. 前提条件・制約事項

### (1) 前提条件
- **Slack 側の設定**:
  - Slack ワークスペース上に Slack App が作成され、適切な Bot Scope（`chat:write`, `channels:history` 等）が付与された Bot トークン（`xoxb-...`）が発行されていること。
  - Event Subscriptions が有効化され、GAS の Web App URL が Request URL として登録・検証済みであること。
- **スプレッドシートの準備**:
  - ログ出力先となる Google スプレッドシートが事前に作成され、指定のシート名が存在していること。
- **プロパティ設定**:
  - GAS のスクリプトプロパティに以下の 3 つのキーが正しく登録されていること。
    - `SLACK_BOT_TOKEN`: Slack Bot OAuth トークン
    - `SPREADSHEET_ID`: ログ出力先スプレッドシート ID
    - `SS_SHEET_NAME`: ログ出力先シート名

### (2) 制約事項
- **Web App 公開設定**:
  - Slack からの Webhook リクエストを外部から受信するため、GAS のデプロイ設定において「アクセスできるユーザー: 全員（匿名ユーザーを含む）」とする必要があること。
- **Slack API タイムアウト制限**:
  - Slack Event Subscriptions はリクエスト送信から 3 秒以内に HTTP 200 応答を受信しない場合、再送（リトライ）を行う仕様があること（※今後重い処理を追加する際はタイムアウトやリトライ制御に留意する必要がある）。
- **GAS クォータ・制限**:
  - GAS の実行時間制限（1 回の実行につき最大 6 分）および `UrlFetchApp` 等の日次呼び出し制限（クォータ）の範囲内で稼働すること。
